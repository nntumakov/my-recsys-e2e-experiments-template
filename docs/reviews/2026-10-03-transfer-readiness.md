## Spec

### 1. P2: диагностика ranking неверна для вложенных полей и numeric dates

Owner: [RankingConfig.source_diagnostics](../../src/core/transformers/opensearch/jobboard/ranking.py),
строки 191–212; чтение значения — строка 193, ограничение даты строковым типом — 203.

Декларации source допускают реальные имена полей OpenSearch. Для
`ranking.quality` и `ranking.published_at` возвращённый `_source` обычно содержит
объект `ranking`, но код выполняет только `item.fields.get(name)`.

Воспроизведённый вход:

```python
ranking_fields = {
    "quality": {"field": "ranking.quality", "type": "numeric"},
    "published_at": {"field": "ranking.published_at", "type": "date"},
}
fields = {"ranking": {"quality": -3, "published_at": "2099-01-01T00:00:00Z"}}
now_ms = 1790640000000
```

Фактическая диагностика: оба значения `None`, flags —
`missing_source_published_at`, `missing_source_quality`. Значения присутствуют;
ожидаются сохранение значений и `negative_quality`/`future_source_date`.
Полные исходные поля документа при этом не теряются; неверно именно производное
представление `metadata` в research-артефакте.

Для плоского `published_at=4070908800000` (epoch milliseconds, 2099 год)
при том же времени сессии значение сохраняется, но `flags=[]`: будущая дата
проверяется только при строковом представлении.

Нарушенный контракт: [spec 006](../specs/006-query-and-painless-candidates.md),
строки 204–206 — будущая дата и отрицательный quality помечаются в диагностике;
638–640 — metadata описывает возвращённые source values.

Исправление должно принадлежать чтению/интерпретации source metadata и учитывать
разницу между source paths и doc values. Нельзя делать вывод об отсутствии
doc values по отсутствию значения в `_source`.
Проверка исправления: плоские и вложенные поля, ISO-дата и epoch milliseconds,
настоящий missing/null, сохранность `fields` и соответствующие anomaly flags.

### 2. P2: повреждённые research sort/timing принимаются как успешный ответ

Owner: [observe](../../src/integrations/opensearch/evidence.py), строки 30–32, 38–53.

Для C3 проверяются число sort keys, числовой первый ключ и непустой строковый
последний. Средний ключ `_score` допускает произвольную строку: ответ с
`sort=[0, "invalid_score", "1"]` и корректным `_score=1.0` успешно проходит `observe`
и становится экспортируемой `ObservedSERP`.

Также явное `took: null` принимается как отсутствие `took`. Это меньший по влиянию
случай того же пробела внешней валидации.

Нарушенный контракт: [spec 006](../specs/006-query-and-painless-candidates.md),
строки 642–643: «optional server_took=null только если допустимый ответ действительно
не содержит took. Поля numeric валидируются».

Оба случая воспроизведены прямым вызовом `observe(OpenSearchResult(response), ...)`.
Это дефект обработки повреждённого ответа; свидетельств, что настоящий OpenSearch
возвращает такой ответ, нет. Валидные ответы не объявляются сломанными.

Проверка исправления: строка/bool/нечисловое значение в позиции score отклоняется
до присваивания items и экспорта; допустимый null score сохраняет прежний контракт;
отсутствующий `took` допускается, явный некорректный `took` отклоняется.

## Что остаётся до уверенного переноса

1. Исправить два подтверждённых несоответствия и добавить проверки существенных
   failure paths. Повторить релевантные tests и обязательные локальные gates.
2. На целевой машине выполнить `poetry check --lock`, чистую `poetry install`
   и запуск проектного kernel/CLI. Проверить, что notebook использует именно это
   окружение; Jupyter намеренно не включён в runtime dependencies.
3. Зафиксировать реальный source profile: версия OpenSearch, URL/auth, text fields,
   типы и доступность doc values для C2/C3, значения категорий, уникальный stable id.
   Не подменять декларацией source фактическую совместимость mapping.
4. Выполнить разрешённый search smoke для реально используемых вариантов.
   Для C2 нужны combined и используемые single-signal/rescore scripts; для C3 —
   строгий порядок категорий, lexical score и stable tie-break; для C4/C5 —
   исходный текст, квалификации, отрицания и контролируемые исправления.
   Проверить реальные JSON/CSV и пустую выдачу. Один basic multi_match smoke
   не подтверждает все эти возможности. Изменять настройки кластера не требуется.
5. Если перенос подразумевает выбор рабочего ранжирования, отдельно принять его
   качество и latency на реальных запросах/разметке. Число синтетических cases,
   rank shifts и успешная компиляция DSL не являются такой приёмкой.

приёмку. Новая архитектура, зависимости или расширение продуктового scope для
устранения найденных ошибок пока не обоснованы.
