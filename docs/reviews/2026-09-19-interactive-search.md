## Standards

### S1. P2 — очистка временного файла подменяет исход экспорта

Место: [JSONExporter.export](../../src/components/reporting/exporters/json.py),
строки 28–31. После `os.link` выполняется безусловный `temporary.unlink()` в finally.

| Контролируемый сбой | Наблюдаемый результат |
| --- | --- |
| Link успешен, unlink выбрасывает PermissionError | Export сообщает ошибку, хотя полный целевой JSON уже опубликован |
| Link выбрасывает OSError/FileExistsError, unlink выбрасывает PermissionError | Наружу выходит ошибка cleanup; исходная причина остаётся только в `__context__` |

Воспроизведение с настоящим временным каталогом подтвердило `published=True`
в первом случае и `published=False` во втором. Верхний CLI намеренно не печатает
цепочку исключений, поэтому первичная причина во втором случае практически теряется.

Нарушается правило сохранения исходной ошибки и явных failure semantics
(глобальные инженерные инструкции, §7). Атомарность и no-overwrite сами по себе
работают: замечание **не означает повреждение JSON или потерю существующего файла**.
Сбой редкий — например, изменение прав или ошибка файловой системы между операциями;
один из reviewers оценил его как P3. P2 здесь относится к неверному исходу операции
при такой неисправности, а не к частоте проявления.

Минимальное исправление: считать успешный link точкой публикации, сохранять
первичную ошибку при сбое cleanup до публикации; после публикации сообщать
неудачную очистку отдельным безопасным warning без превращения завершённого
экспорта в failure. Не скрывать оставшийся временный файл. Новая abstraction
или замена atomic hard-link механизма не нужны.

Необходимые tests: успешная публикация + failed unlink; failed link/fsync +
failed unlink, включая существующий целевой файл. Текущие reporting tests
инъецируют fsync/link failure только при успешном cleanup.

### Суждение: диагностика CLI слишком общая

[run.py](../../src/run.py), строки 20 и 29–30, выводит только фазу и имя класса
исключения. HTTP 401, timeout и JSON failure выглядят одинаковым RuntimeError;
разные ошибки сборки — одинаковым InstantiationException.

Это ухудшает настройку на устройстве с настоящим прокси, но не считается отдельным
нарушением: политика явно описана в development.md и предотвращает утечки
resolved credentials. Возможное улучшение — передавать только проверенные
безопасные причины/коды владельцев ошибок и различать execution/export.
Печатать произвольные `str(exc)` или traceback вместо этого нельзя.

## Spec

### R1. P2 — URL с пустым query/fragment отправляет запрос не в search

Место: [OpenSearchIntegration](../../src/integrations/opensearch/client.py),
строки 59–60 и 80. Проверка использует truthiness `parts.query/parts.fragment`.
Пустая компонента не отклоняется, затем путь добавляется к исходной строке.

Настоящий `urllib.request.Request` с mocked opener даёт:

| URL конфигурации | Request.selector |
| --- | --- |
| `http://example.invalid/proxy?` | `/proxy?/jobs/_search` |
| `http://example.invalid/proxy#` | `/proxy` |

В первом случае search-путь стал query, во втором — fragment, который не
отправляется серверу. Это конкретное нарушение spec 001: URL без query/fragment
и отклонение некорректной конфигурации до запроса. Это не утверждение, что обычный
правильно заданный URL работает неверно.

Минимальное исправление: отклонять буквальные `?` и `#`, даже с пустыми значениями.
Percent-encoded `%3F`/`%23` в пути не следует запрещать этим правилом.
Tests должны проверять отказ конструктора для обоих случаев без HTTP-вызова.

### R2. P2 — некорректные JSON-числа обнаруживаются после успеха pipeline

Место: [OpenSearchIntegration.search](../../src/integrations/opensearch/client.py),
строка 87. Обычный `json.loads` принимает `NaN`, `Infinity`, `-Infinity`, хотя
эти литералы не входят в JSON. Проверка конечности score не защищает другие поля.

Воспроизведение: стандартная оболочка ответа, валидный id/score, поле
`_source.salary: NaN`. Настоящий transformer успешно возвращается и заменяет
прежний `data.items`. Затем терминальный `json.dumps(..., allow_nan=False)`
выбрасывает ValueError. Raw response с таким числом в aggregations также
возвращается как успех. Response при этом корректно закрывается.

Проверены NaN, Infinity и числовой токен `1e400`. Последний синтаксически допустим
в JSON, но превращается в Python inf и вызывает тот же поздний сбой. Здесь две
разные причины: недопустимые литералы и переполнение выбранного числового типа.

Контракт spec 001 требует выявлять JSON failures на внешней границе и сообщать
безопасный RuntimeError. Проблема — слишком позднее обнаружение некорректного
представления, а не утверждение, что transformer одновременно бросил исключение
и изменил payload: он как раз завершился успешно. Нормальный OpenSearch не обязан
возвращать такие литералы; это проверка обещанной защиты от повреждённого ответа.

Минимальное исправление: строгий `parse_constant` для запрещённых литералов;
для отсутствия любых nonfinite float — finite-checking `parse_float`, учитывающий
`1e400`. Не нужен рекурсивный validator или изменение произвольного DSL.
Tests: source и aggregation values, закрытие response, прежние items остаются
неизменными при отказе на декодировании. Сейчас проверяется только nonfinite score.

## Эффективность и лаконичность

Локальное синтетическое измерение: 20 запросов × 100 вакансий; compact JSON
2 597 270 байт, форматированный — 2 953 892 байта. Измерения этапов одиночные,
с включённым tracemalloc; пик — дополнительные аллокации этапа, не RSS процесса.
У exporter файловый I/O заменён sink; результаты не характеризуют скорость диска,
терминала или сети. Повторяющиеся неизменяемые строки разделялись между записями.
Payload каждого hit: id `q-i`, score 1.0, title `Vacancy i`, description
`"Python developer. " * 64`, tags `["python", "remote"]`, location `{city: "Berlin"}`.
До каждого этапа выполнялись gc.collect и tracemalloc.start; длительность
измерялась perf_counter, предыдущие результаты оставались живыми. Exporter вызывался
с подменёнными NamedTemporaryFile/fsync/link/unlink; файлов benchmark не создавал.

| Этап | Время | Дополнительный пик |
| --- | --- | --- |
| Снимки записей сессии | 75,7 ms | 1,28 MiB |
| Конструктор SearchArtifact | 70,6 ms | 1,84 MiB |
| to_dict | 72,7 ms | 1,83 MiB |
| JSON-форматирование готового dict | 250,3 ms | 8,06 MiB |
| Exporter без файлового I/O | 325,7 ms | 9,30 MiB |

Измерение не обосновывает архитектурный performance-refactor. Копии отделяют
результат изменяемого transformer, вход артефакта и данные, выдаваемые to_dict.
Их удаление нарушило бы принятые ownership-контракты. Сессия накапливается в памяти
до EOF; это линейный расход по общему объёму результатов, выбранный текущим контрактом.

Две локальные необязательные оптимизации:

- [json.py](../../src/components/reporting/exporters/json.py), строка 24:
  `content + "\n"` создаёт ещё одну полную строку. В замере это около 2,82 MiB
  и 0,6 ms. Два write устраняют копию без смены формата и порядка валидации.
- [data.py](../../src/core/transformers/data.py), строки 34–36:
  shallow copy делает dict, который конструктор сразу копирует повторно.
  Достаточно оставить создание внешнего dict конструктору.

Повторный append tuple имеет O(N²) для N добавлений, но первый сценарий добавляет
один QueryFilter. Замеры 100/1 000/10 000 добавлений: примерно 0,2/2,4/173 ms;
оснований менять предписанное immutable представление для текущей задачи нет.
Registry проверяет граф один раз за O(V+E), не перед каждым запросом.

DSL-builder, DFS registry и запрет redirect имеют конкретные контракты.
Выносить новые helpers, вводить Service/Factory или удалять необходимые проверки
внешнего ответа ради уменьшения числа строк не рекомендуется.

## Проверка ZERO-SPEC

| Требование | Вердикт и evidence |
| --- | --- |
| Сохранить исходную структуру абстракций | Все 46 исходных файлов src и 27 объявленных классов присутствуют в тех же файлах; проверено сравнением AST с HEAD |
| DDD и основные понятия | Domain documents, collections, filters; словарь CONTEXT; отдельные владельцы поиска, транспорта, преобразования и экспорта |
| Лаконичность, минимум helpers/checks | В целом соблюдено; проверки у конфигурации, входа и внешнего ответа; замечания локальны |
| Свободные эксперименты, типизированные части | SearchExperiment.run — обычный Python-сценарий; typed transformer/integration/artifact contracts |
| Hydra и интерполяции | Один instantiate; интерполяции connection/search/output в текущих конфигах |
| Код реализаций в src | Весь прикладной код находится в src; tests отдельно согласно последующей spec |
| Вложенная организация | configs/experiments/vacancy-search/interactive/001-basic.yaml и исходная иерархия src сохранены |
| Старые ветки как контекст | Историческое исследование выполнено ранее; старый ComponentRegistry и runtime не перенесены автоматически |
| Прокси, только search, стандартный DSL | Один POST search, произвольное тело DSL, URL/auth параметризованы; R1/R2 относятся к обработке ошибочных входов |

Не считаются дефектами: маркерные Vacancy/SERP/Base-типы, deferred метрики,
отсутствие автоматического поиска маршрута, обязательство будущего фильтра быть
immutable, анализ registry только явных PipelineTransformer и отсутствие общей
транзакции нескольких exporters. Это согласованные ограничения.

## Проверки и следующий шаг

Повторно выполнены: 61 pytest test, Ruff check, Ruff format --check, ty check,
git diff --check. Все прошли. Lockfile использует публичный pypi.org;
привязки к частному registry в источниках пакетов не обнаружено.
Live smoke не выполнялся: реальный прокси недоступен на этом устройстве.

Зелёные gates не покрывают три воспроизведённых дефекта. Следующий набор правок
может быть узким: R1, R2, S1 и их focused tests. Две оптимизации аллокаций
независимы и имеют низкий приоритет. Изменение стратегии snapshot, новых режимов,
формата результата или структуры абстракций для этих исправлений не требуется.

Дополнительные полезные regression cases без отдельного доказанного дефекта:
валидный первый hit + повреждённый последний (отсутствие частичной замены items),
мутация вложенного результата to_dict (глубина snapshot, а не только clear верхнего dict).

Итого: Standards — 1 подтверждённый дефект (исход cleanup после экспорта);
Spec — 2 подтверждённых дефекта (неверный endpoint при пустых delimiters и
поздний отказ числового JSON). Архитектурного переписывания не требуется.
