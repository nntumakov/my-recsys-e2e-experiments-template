# Query Understanding: понятия и консервативное исправление ввода

Первый продуктовый профиль — рабочие профессии
на русском языке. [Приложение 006A](../specs/006-blue-collar-content.md) задаёт
обязательный актуальный контент и уточнения: новые slots графика/квалификаций,
вводные фразы, контекстные rewrites и punctuation keys для layout. IT/RU-EN примеры
этой исследовательской записки объясняют механизмы и остаются регрессиями;
они не заменяют новый наполненный профиль и его приоритеты.

Дата: **2026-09-29**. Исследование для кандидатов 4 и 5
[spec 006](../specs/006-query-and-painless-candidates.md). Это обоснование
проектных решений, а не доказательство улучшения качества на реальном индексе.

Реализация spec 006 поставлена: [slot parser](../../src/components/query/jobboard/slots.py),
[rewriter](../../src/components/query/jobboard/rewrite.py) и
[slot compiler](../../src/core/transformers/opensearch/jobboard/slots.py) расширяют
исходный каркас. Поставленный контент задаёт 006A; ранние IT-примеры ниже объясняют
выбор механизмов, а не состав обязательного русского словаря.
Локальные свидетельства и границы готовности — в [development.md](../development.md).

Это обоснование контролируемого словаря; не утверждение эквивалентности любых похожих строк. |

**Граница переноса:** источники не доказывают эффективность наших RU/EN-правил,
численных boosts, порогов исправления или словаря. Ни Q4, ни Q5 не обосновывают
автоматическое превращение свободного текста в строгий фильтр. Все конкретные
правила ниже — проектные решения spec 006 (spec choice),
а не нормативные требования источников или оценённые параметры.

## Исходная реализация перед spec 006

В [ModularQueryParser](../../src/components/query/jobboard/parser.py) уже есть
последовательность stages, merging пересечений, ambiguity, бюджеты и отключение
структурированной интерпретации при неподдерживаемом синтаксисе.
[LexiconQueryStage](../../src/components/query/jobboard/lexicon.py) распознаёт
`role`, `skill`, `seniority`, `work_mode`, `location`, хранит `rule_id`, canonical,
curated equivalents/translations и требует контекста для неоднозначных forms.
[NormalizeText](../../src/components/query/normalization.py) выполняет NFKC,
casefold и нормализацию пробелов, но не исправляет опечатки и раскладку.

В [jobboard query builder](../../src/core/transformers/opensearch/jobboard/query.py)
уже есть исходная literal-ветка, aliases через `dis_max`, concept coverage,
тематический gate, мягкие boosts для attributes и ограниченная fuzzy-ветка.
В исходном compiler концептуальные группы используют общий список полей и общие веса.
Fuzzy применяется к подходящим residual-токенам, не к защищённым или неоднозначным
spans. Поэтому «добавить parser/aliases/fuzzy» не является новым экспериментом.

## Кандидат 4: распознать понятия и направить их в подходящие поля

**Вопрос:** можно ли уменьшить ложные совпадения по длинному описанию, сохранив
вакансии, где разные части запроса выражены в разных полях?

`python backend developer удалённо` содержит не четыре равноправных слова:
`backend developer` — роль, `python` — навык, `удалённо` — предпочтение формата.
Одинаковый boost всему запросу по полю title плохо выражает это различие.
Практика Q4 — разделить составляющие намерения; практика Q5 — узнавать разные
обозначения одного понятия. Перенос в проект: словарь + типизированные hints +
явная компиляция групп, без LLM, vector storage и изменений индекса.

### Стартовое поведение, выбранное в spec 006

- `role`: title с весом 4, description с весом 1.
- `skill`: title с весом 2, description с весом 1, optional skills с весом 3.
  Отдельное skills-поле не требуется: поставляется готовый title/description preset.
- `seniority`, `work_mode`, `location`: только мягкие scoring clauses в явно
  настроенных текстовых полях с начальным boost 0.2; не создавать `TermFilter` из распознанного текста.
- Неизвестные residual terms: существующие общие поля; сохранять исходные слова.
- Имена полей физические и задаются в одном source-профиле. Ролевые группы
  ссылаются на эти имена; отсутствие настроенного обязательного поля — ошибка
  конфигурации до HTTP. Не подставлять предполагаемые `skills` или `location`.
- Внутри одного понятия literal и aliases — альтернативы с `dis_max`,
  `tie_breaker=0`; literal weight 1, curated alias weight 0.7 как стартовая
  гипотеза. Многословный alias компилировать фразой, а не набором независимых OR.
- Между тематическими группами и residual — coverage: все группы при их числе
  1–2, `ceil(0.75 * n)` при большем числе. Attributes в denominator не входят.
- Исходная literal-ветка остаётся доступной; coverage относится к concept-ветке,
  поэтому её нельзя описывать как безусловную гарантию покрытия всей выдачи.
  Существующий gate «хотя бы один подтверждённый topic» сохраняется явно.
- Ambiguous hint не расширять; unknown/ambiguous fragment остаётся literal.
  Неподдерживаемое отрицание или syntax отключает structured interpretation
  согласно существующей политике, а не превращается в выдуманный запрос.

Числа — начальные ручки сравнения, не оценённые параметры. `boost=0.7` для alias
не гарантирует, что literal-документ всегда выше: IDF и статистики полей различны.
Routing означает набор полей и веса, а не обязательное наличие слова в title.
`best_fields` по всему запросу не заменяет concept-level coverage: Q2 описывает
field-centric семантику, при которой «роль в title + навык в skills» может вести
себя иначе. Явные отдельные группы дают наблюдаемый контракт без зависимости
от совместимости анализаторов `cross_fields`.

### Фактурные случаи для обсуждения с продактом

| Запрос/документ | Что сравниваем | Риск |
| --- | --- | --- |
| `python backend developer`; title=`Backend engineer`, skills содержит Python | Роль и навык находятся в разных полях; aliases роли добавляют доступный путь | Alias `engineer` слишком широк, если в словаре потерять backend |
| Тот же запрос; title=`Account manager`, description перечисляет Python команды | Более слабый score role-сигнала в description | Веса уменьшают риск, но не доказывают исключение документа |
| `data scientist`; title=`Data engineer` | Сохранение многословного понятия и curated equivalents | Не объявлять соседние профессии синонимами |
| `go`; затем `go developer` | Abstention без контекста, распознавание с контекстом | Не трактовать любое английское go как язык |
| `senior python remote` | Мягкие level/work-mode сигналы отдельно от тематики | Слова в описании не подтверждают структурированные атрибуты вакансии |
| `C++`, `C#`, `.NET`, `1С` | Сохранение защищённых обозначений | Если индекс потерял символы при анализе, parser их не восстановит |

**Delta поставки:** kind-specific routing и веса, законченные RU/EN starter
правила, trace распознанных/неоднозначных spans и причин, показ coverage и
сформированного DSL в сравнении. Повторно писать нормализатор или новый parser
рядом с существующим не нужно.

## Кандидат 5: ограниченно восстановить испорченный ввод

**Вопрос:** можно ли получить полезный запрос из опечатки, раскладки или
транслитерации, не подменяя уверенно введённую профессию другой?

Q3 описывает близость термов по редакционному расстоянию. Она не превращает
`знерщт` в `python`: это несколько систематических замен клавиш. Также fuzzy
не знает, какая строка является подтверждённым названием навыка. Поэтому
новая гипотеза — application-side восстановление только в конечный curated
словарь, с проверяемым отказом от интерпретации. Это отдельная практика от C4:
C4 понимает корректно введённое, C5 восстанавливает вероятное написание.

### Детерминированный starter — spec choice

1. Сохранить original text; получить existing normalized text и spans.
   Известные словарные spans, protected terms, короткие аббревиатуры, токены
   с цифрами/техническими символами, mixed-script и unsupported syntax
   автоматически не исправлять. Стартовая длина токена — от 5 до 64 букв.
2. Для неизвестного alphabetic-токена построить кандидаты **независимо**:
   RU↔EN keyboard mapping; явные направленные curated rewrite/transliteration pairs;
   edit distance ≤1 до разрешённых vocabulary surfaces, включая соседнюю
   транспозицию как одну операцию. Не выполнять каскад layout→typo→alias.
3. Keyboard candidate принять только при точном совпадении с однозначным
   разрешённым vocabulary surface. Transliteration — конечные entries
   вроде `razrabotchik → разработчик`, без общего предположения, что любая
   латиница есть русский транслит. Написания вроде `питон` уже являются
   ordinary aliases C4 и не требуют нового rewriting.
4. Собрать все кандидаты всех каналов до выбора. Если они указывают на разные
   canonical concepts — abstain с причиной `ambiguous_candidates`.
   Если это несколько forms одного concept, выбрать детерминированно:
   curated → layout → spelling, затем меньшая distance и lexical target.
   Trace сохраняет варианты; до проверки ambiguity список не усекается.
   Неоднозначность хотя бы одного span отклоняет весь rewrite запроса.
   Не брать первый результат словарного обхода и не выбирать случайно.
5. Разрешить максимум два исправляемых непересекающихся span и одну
   исправленную полную строку на запрос. Обе принятые замены применяются вместе,
   остальные слова и их порядок сохраняются. При более двух подходящих spans —
   abstain для всего rewriting с `rewrite_budget_exceeded`, без выбора первых двух.
6. Повторно разобрать rewritten text через C4 с новыми offsets. Построить ветки
   C4(original) с весом 1 и C4(rewritten) с boost 0.65, объединить
   `dis_max(tie_breaker=0)`. Attributes остаются мягкими сигналами C4; одинаковые
   явные hard filters применяются снаружи к обеим веткам, inferred filters нет.
   Не включать fuzzy и повторное исправление rewritten text; не складывать
   score разных механизмов за одно исправление. Общий leaf budget 128 действует
   на весь запрос. Переполнение — ошибка до HTTP, не усечение второй ветки.

Кандидат 5 по решению spec построен поверх C4: сравнение **C4 ↔ C5**
изолирует влияние rewriting при одинаковых routing, aliases и budgets.
`rewrite-off` и отсутствие принятого исправления дают ровно C4(original),
без пустой второй ветки. Можно дополнительно показать существующий `fuzzy`
как контроль; C1 не требуется как основной контроль для C5.
Индексные термы и частоты не нужны: словарь конечный, локальный и поставляется
с конфигами. Нет сетевого spellchecker, suggest-запроса, LLM или загрузки модели.

### Обязательные примеры

| Ввод | Ожидаемое решение | Причина |
| --- | --- | --- |
| `pyhton developer` | Вариант `python developer`; original сохранён | Одна транспозиция, известная цель Python |
| `знерщт developer` | Вариант `python developer` | Точное преобразование EN-клавиш, набранных в RU-раскладке |
| `razrabotchik python` | Вариант `разработчик python` | Явная starter-запись транслитерации |
| `python developer` | Без изменения | Известные формы не «улучшаются» |
| `Go`, `R`, `QA`, `C++`, `.NET`, `1С` | Без изменения | Короткие/защищённые обозначения |
| `javx` | Без изменения | Короче minimum length; не гадать Java/иное |
| Неизвестное имя компании | Без изменения, если нет единственной разрешённой цели | Нет blanket spellcheck произвольных слов |
| Синтетический токен в 1 edit от двух concept IDs | Abstain | Тестирует ambiguity без случайной зависимости от текущего словаря |
| Две однозначные исправимые опечатки | Один rewritten query с двумя заменами | Budget = 2 spans / 1 variant |
| Три однозначные исправимые опечатки | Abstain, original branch | Не брать случайные первые две |
| `аналитк данных` | `аналитик данных`, если подтверждена целая recognition phrase | Токен фразы не становится самостоятельной профессией |

Вес 0.65 не гарантирует, что все original matches выше rewritten matches:
BM25 разных термов имеет разные шкалы. Для строгого original-first порядка
нужна отдельная согласованная политика ранжирования; в этот кандидат она не
входит. Новая rewrite-ветка повышает возможный recall, но не гарантирует
наличие результата без знания индекса. Ошибочная замена имени или термина
остаётся главным риском, поэтому trace и abstention — часть продукта.

### Фразы, контекст и неоднозначность

Spelling vocabulary выводится из текущих unambiguous role/skill recognition
forms, включая токены многословных forms. Совпадение исправленного токена само
по себе недостаточно: `аналитк данных` подтверждает понятие через целую
`аналитик данных`, а `данных` не становится самостоятельной ролью.
Provenance хранит concept ID и целую recognition phrase. Разрешение фразы
проверяется в восстановленном контексте; generic role не разворачивается во
все специализации. Сначала whole longest phrase того же kind приоритетнее generic concept;
при одинаковой длине и разных concepts — abstain. Неоднозначность любого span
отклоняет весь rewrite, даже если другой span исправляется уверенно.
Так literal preservation не зависит от порядка обхода spans.

Seed поставляется полностью: RU/EN map для букв, минимум 12 направленных
curated rewrite/transliteration pairs, finite vocabulary из существующего
lexicon и явно добавленные недостающие concepts. Например, `разработчик`
добавляется как generic recognition concept с отрицательным примером;
не следует считать эту цель уже существующей только по наличию слова
в многословных названиях. Для каждого rewrite — положительный пример и
пример отказа; переключатели spelling/layout/curated независимы.

## Граница локальной реализации

Контракт завершённости включает код, Hydra-композиции всех кандидатов,
конечные starter lexicons и rewrite rules, рабочие варианты полей/boosts на
локальной fixture, notebook/CLI для показа original/normalized/rewritten,
parsed hints, причин abstention, routing, параметров и итогового DSL. В реальном
окружении пользователь подставляет подключение и физические названия полей,
а не дописывает parser, таблицу раскладки или алгоритм исправления.

Локальные проверки обязательны: точные output/spans, неизменность protected
термов, budgets, неоднозначность между каналами, фильтры, deterministic ordering,
отсутствие HTTP при плохом конфиге, композиция Hydra и передача тела запроса
локальному HTTP-серверу. Нужны контрпримеры, где расширение запрещено, а не
только happy-path YAML snapshots. Демонстрационный вывод должен явно отличать
локальную диагностику от ответа реального поискового движка.

Без настоящего OpenSearch проверяется алгоритм и контракт запросов, но не
анализ конкретного индекса, исполнение DSL/Painless, latency или реальное
ранжирование. Эти неизвестные не оставляют за собой недописанный код и не
превращают локальную acceptance в обещание production-качества.
