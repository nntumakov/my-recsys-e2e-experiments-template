# 005. Исследование поисковых запросов

Статус: **локальная реализация поставлена; проверка реального контура открыта**.

Результаты проверок и ограничения среды — в [development.md](../development.md).

## Outcome

Исследователь использует одну Hydra-композицию в ноутбуке и при пакетном
исследовании набора запросов. Можно менять формат поискового запроса, проверять
отдельный пример и получать артефакт по набору без обязательной разметки релевантности.

## Одиночный поиск

`SearchExperiment.search(text, *, context=None, filters=()) -> SERP` выполняет
один поиск без терминального ввода, печати и файлового экспорта. Вызов использует
сконфигурированные registry/pipeline, context и статические filters эксперимента.
Контекст вызова дополняет и переопределяет верхнеуровневые свойства исходного
контекста. Фильтры вызова добавляются к статическим условиям с AND-семантикой;
они не могут содержать QueryFilter. Единственный QueryFilter создаётся из text.

Каждый вызов получает независимый payload с глубокой копией контекста. Пустой
текст и QueryFilter среди дополнительных условий отклоняются до pipeline.
Возвращается независимый снимок завершённой SERP; незавершённые ветки и иная
коллекция являются ошибкой. Ошибки поиска сохраняют свой смысл и передаются
вызывающему коду. Следующий ручной вызов возможен без пересоздания эксперимента.

Терминальный `run()` использует тот же метод. Прежние EOF/ошибка/Ctrl-C,
формат searches.json и атомарный no-overwrite export сохраняются.

Ноутбук использует Hydra Compose API и явное отключение exporters. Изменение
конфига требует новой instantiate; Python-объекты не являются live-view конфига.
Jupyter не добавляется в runtime-зависимости проекта.

Оба OpenSearch leaf transformer раскрывают `build_query(data)`: построение того
же DSL, который использует transform, без HTTP и изменения payload. Это просмотр
одного поискового листа, а не исполнение произвольного pipeline. Для fused можно
отдельно исследовать lexical_leaf и parsed_leaf. Общий BaseTransformer и payload
не получают обязательного нового интерфейса или query-plan.

## Пакетное исследование

Вход — CSV с `id,text`, выход — CSV с результатами поиска по набору.
Offline-выгрузка DSL не входит в этот сценарий.

`BatchSearchExperiment` получает сконфигурированный SearchExperiment: `run()` читает
весь входной CSV, проверяет его и последовательно вызывает его `search()` для каждой
строки. Registry, pipeline, context и filters настраиваются теми же Hydra groups.
Разметка релевантности и метрики не требуются. Поддерживаются все существующие
pipeline, включая fused; внутри него сохраняются полная глубина кандидатов и RRF.

Входной CSV содержит ровно заголовки `id,text` (порядок колонок несущественен),
непустые уникальные id и непустые тексты. Пробелы по краям id/text удаляются.
Поддерживаются UTF-8 с optional BOM, стандартное quoting и переносы внутри поля.
Отсутствующие/лишние столбцы, пустой набор и неверные строки — ошибка до первого
HTTP. Вся локальная структурная проверка набора предшествует поискам; ошибки
конкретного parser/compiler могут возникнуть при обработке соответствующей строки.

Выходные колонки: `query_id,query,rank,document_id,score,fields`. Порядок строк —
порядок входных запросов, затем порядок SERP; rank начинается с 1. `fields` содержит
полный JSON объекта полей документа с сохранением вложенных значений. Null score
представляется пустой ячейкой. У пустой выдачи одна строка с query_id/query и пустыми
остальными ячейками. Отсутствие результата отличается от сбоя: ошибка прекращает
run без публикации CSV; выполненные read-only HTTP не откатываются.

BatchSearchArtifact владеет независимым снимком результатов и представлениями
JSON/табличных строк. SearchCSVExporter владеет CSV-сериализацией и использует
тот же механизм атомарной публикации без overwrite, что и JSONExporter.
Batch `run()` возвращает артефакт без записи; CLI вызывает exporters только после
полного успеха. Файлы CSV публикуются в UTF-8. Credentials и полный resolved config
в результаты не включаются; тексты запросов и все поля документов входят явно.

Форматы прежних searches.json/comparison.json не меняются. Новые Hydra wrappers
для basic/jobboard batch оставляют глобальный default прежним. Поставляются
небольшой вымышленный входной CSV и ноутбук в src с выбором конфигурации,
просмотром DSL через существующий compiler, ручным поиском и пакетной выгрузкой.
Ноутбук использует публичные методы; новая инфраструктура исполнения не вводится.

Не входят: streaming/resume/retries, параллельные запросы, XLSX, автоматическая
разметка, новые retrieval-алгоритмы и изменение протокола OpenSearch.

## Acceptance evidence

- Одиночный поиск через реальную Hydra-композицию и локальный HTTP.
- Сохранение статических и дополнительных условий, изоляция повторных вызовов.
- Ошибки входа до pipeline, отсутствие печати/экспорта при ручном вызове.
- Прежние CLI и comparison tests проходят без изменения их контрактов.
- CSV → Hydra → HTTP → полная SERP/RRF → CSV, включая несколько запросов,
  Unicode/quoting, вложенные fields, пустую выдачу и null score.
- Невалидный вход до HTTP, сбой второго поиска без частичного CSV, сохранение
  существующего результата при повторной публикации.
- Исполняемый пример ноутбука, Ruff, ty, pytest и проверка ссылок.
- Реальный OpenSearch остаётся отдельной внешней проверкой.
