# 007. Корректность research metadata и валидации ответа

Статус: **реализована локально 2026-10-03; внешняя приёмка переноса не выполнена**.

Основание — [аудит готовности от 2026-10-03](../reviews/2026-10-03-transfer-readiness.md).
Проверенный baseline: `b7be99ebb95249032a892e2a3f4a43ce68b7aaae`, ветка `master`.
Аудит выявил две группы дефектов, ниже они разделены на четыре проверяемых требования.
474 прошедших теста baseline не покрывают эти воспроизведения.

Эта spec уточняет локальное исполнение [006](006-query-and-painless-candidates.md),
а не меняет её исследовательские гипотезы или границу поставки.
Текущая готовность и новое evidence фиксируются в [development](../development.md),
владельцы и действующие технические контракты — в [архитектуре](../architecture.md).
R1–R4 реализованы; свидетельства для A1–A12 и результаты gates находятся в
[development](../development.md). Раздел 10 сохраняет порядок исполнения этапа;
раздел 11 остаётся планом отдельной внешней проверки.

## 1. Наблюдаемый результат

Исследователь получает достоверную локальную диагностику возвращённого `_source`
при обычных плоских и вложенных ranking-полях, включая дату в epoch milliseconds.
Повреждённые research sort/timing не превращаются в успешный результат поиска
и не попадают в экспорт.

| ID | Текущее нарушение | Требуемое поведение |
| --- | --- | --- |
| R1 | `ranking.quality` ищется только как буквальный верхнеуровневый ключ | Значение доступно также по пути через вложенные объекты; существующие буквальные ключи совместимы |
| R2 | Будущая numeric date сохраняется без предупреждения | Конечная числовая дата интерпретируется как epoch milliseconds и сравнивается с фиксированным временем сессии |
| R3 | C3 принимает `sort=[0,"invalid_score","id"]` | Средний ключ допускает только конечное число или ранее поддержанный `null` |
| R4 | Явный `took:null` неотличим от отсутствующего поля | Отсутствие допускается; присутствующее поле обязано быть неотрицательным целым, не bool |

Критерий успеха — исправленные наблюдаемые значения/ошибки на составном пути
Hydra → HTTP → transformer → research artifact → export, при сохранении прежних
валидных сценариев. Совпадения с формой реализации для приёмки недостаточно.

## 2. Границы изменения

### Входит

- Чтение source values активных ranking signals и диагностика будущей даты.
- Проверка research sort score и различение missing/invalid `took`.
- Адресные regression tests, составной HTTP/экспорт и атомарность отказа.
- Обновление canonical contracts и статуса после реализации.
- План внешней проверки переноса с отдельным результатом и ограничениями.

### Не входит

- Изменение retrieval, QU, ranking-формул, Painless source, boosts или defaults.
- Новые source mappings, introspection API, field aliases или language для путей.
- Пересчёт server score, сортировка результатов на клиенте, восстановление doc values.
- Новые форматы экспорта, schema version, конфигурационные режимы или зависимости.
- Миграция старых артефактов, переработка notebook UI, backend, retries/resume/streaming.
- Поддержка массивов объектов как источника single-valued ranking signal.
- Развёртывание OpenSearch, изменение индекса/кластера или заявления о качестве поиска.

Факт исправления diagnostics не означает, что серверный ranking раньше вычислялся
неверно: он использует doc values, а проверяемая функция читает возвращённый `_source`.

## 3. Владельцы и направление данных

| Поведение | Владелец | Ограничение |
| --- | --- | --- |
| Доступ к source value и flags | `RankingConfig.source_diagnostics` в `core/transformers/opensearch/jobboard/ranking.py` | Не менять документ, mapping или script params |
| Проверка timing/sort и snapshot | `observe` в `integrations/opensearch/evidence.py` | Проверить ответ полностью до возврата `ObservedSERP` |
| Публикация SERP в payload | `ResearchSearchTransformer.transform` | Присвоить items только после успешной конвертации и diagnostics |
| Остановка compare/batch и экспорт после успеха | `ResearchExperiment`, `BaseExperiment`, существующие exporters | Не переносить в них разбор сетевого ответа |
| Представление результата | `ResearchArtifact` | Сохранить schema и snapshot semantics; не чинить входные данные при сериализации |

Нужные локальные функции допустимы внутри владеющего модуля, если у них есть
ясный контракт и тестовая ценность. Отдельный registry, generic JSONPath resolver,
`utils`-модуль или новый service для этой задачи не требуются.
Источник истины для полей остаётся `SourceProfile.ranking_fields`, для времени —
существующий `now_ms`. Дублирующие настройки не добавляются.

## 4. R1 — разрешение source paths

### 4.1. Правило доступа

Для полного имени из source declaration:

1. Если в верхнеуровневом `item.fields` есть **точно такой ключ**, взять его значение.
   Проверяется наличие ключа, а не truthiness или отличие от `None`.
2. Иначе разделить имя по точкам и пройти соответствующие вложенные JSON-объекты.
   Каждый сегмент — буквальный ключ объекта; числовой сегмент не является индексом.
3. Если сегмент отсутствует или промежуточное значение не является объектом,
   source value по этому пути недоступно. Сохранить прежнюю missing-диагностику.
4. Достигнутое значение сохранить глубоким снимком в `metadata.values[role]`.
   Не преобразовывать его в строку или другой JSON-тип ради представления.

Приоритет точного верхнеуровневого ключа сохраняет существующее поведение для
источников, реально возвращающих буквальные ключи с точкой. Если одновременно
существуют такой ключ и вложенный путь, побеждает точный ключ, даже при `null`.
Не вводятся рекурсивный поиск «подходящего» ключа, частично плоские пути,
escaping, wildcard, обход массивов и разрешение коллизии по значениям.

### 4.2. Примеры

Имя поля во всех строках — `ranking.quality`.

| `_source` | `metadata.values.quality` | Flags |
| --- | --- | --- |
| `{"ranking":{"quality":-3}}` | `-3` | `negative_quality` |
| `{"ranking.quality":-2}` | `-2` | `negative_quality` |
| `{"ranking.quality":0,"ranking":{"quality":-3}}` | `0` | Нет `negative_quality` |
| `{"ranking.quality":null,"ranking":{"quality":-3}}` | `null` | `missing_source_quality` |
| `{"ranking":{"quality":null}}` или `{}` | `null` | `missing_source_quality` |
| `{"ranking":[]}` или `{"ranking":5}` | `null` | `missing_source_quality` |

Обычный `quality` продолжает читаться как плоский ключ. Глубина пути не ограничена
одним вложением. Значения `0`, `false` и пустая строка не считаются отсутствием:
flags рассчитываются по прежним правилам конкретного signal, без общего coercion.

Терминальный массив/объект сохраняется как возвращённое значение; из него не
выбирается «первый» или «лучший» scalar. Его интерпретация как single-valued signal
остаётся вне этой spec. Недоступный путь и явный null по-прежнему используют общий
`missing_source_<role>`; новых флагов или различий формата не вводится.

### 4.3. Пределы выводов

`origin=returned_source_not_doc_values` обязателен и неизменен.
Поле `category.keyword` может существовать в mapping/doc values без одноимённого
source value. Нельзя автоматически отбросить `.keyword`, подставить `category`,
прочитать `hit.fields`, запросить mapping или утверждать отсутствие поля в индексе.

Диагностируются только роли из активных `field_params`. Отключённый freshness
или quality не должен начать требовать поле или выдавать missing flags.

## 5. R2 — дата публикации

### 5.1. Поддержанные представления

| Представление source date | Интерпретация |
| --- | --- |
| `int` или конечный `float`, исключая `bool` | Epoch milliseconds; дробная часть не отбрасывается |
| Поддержанная текущим ISO-парсером строка с timezone, включая `Z`/offset | Абсолютный момент времени |
| Поддержанная ISO-строка без timezone | Сохранить `source_date_without_timezone`; не угадывать timezone |
| Неразбираемая строка | Сохранить `unparsed_source_date` |
| Отсутствие или `null` | Сохранить `missing_source_published_at` |

Будущая дата — строго `published_ms > now_ms`; равенство не является аномалией.
Числовое представление сравнивается в миллисекундах без преобразования в локальную
календарную дату, округления, умножения на 1000 или угадывания единицы по длине числа.
Отрицательная epoch date допустима и означает момент до 1970 года.

Числовые строки не получают нового автоматического распознавания. Другие типы
сохраняются как source values и не интерпретируются как дата; в частности, bool
не становится timestamp `0`/`1`. Расширение diagnostic flags для произвольных
несовместимых типов не входит в изменение. Nonfinite JSON по-прежнему отклоняется
существующей внешней границей; diagnostics не должен легализовать такой ответ.

### 5.2. Наблюдаемые инварианты

- `4070908800000` и `"2099-01-01T00:00:00Z"` дают `future_source_date`
  при `now_ms=1790640000000`.
- Эквивалентные строки с разными timezone offsets дают один результат.
- В `metadata.values.published_at` сохраняется исходное представление.
- Плоское и вложенное представления одной даты дают одинаковые flags.
- Порядок flags остаётся детерминированным; повторный вызов не накапливает flags.
- Фиксированное время сессии используется повторно; часы машины не читаются.
- Параметры Painless, исходный `_source` и server score не меняются.

## 6. R3 — sort evidence C3

### 6.1. Типы ключей

Для существующего research-запроса с C3 sort каждый hit обязан иметь массив
ровно из трёх элементов:

| Позиция | Смысл | Допустимое значение |
| --- | --- | --- |
| 0 | Script tier | Конечный `int`/`float`, не bool; сохраняется текущая проверка |
| 1 | Score sort key | Конечный `int`/`float`, не bool, либо `null` |
| 2 | Stable id | Непустая строка; сохраняется уникальность среди возвращённых hits |

`null` в позиции score уже поддержан составным тестом baseline и остаётся валидным.
Он сохраняется в sort evidence и не подменяется нулём, `_score` или первым ключом.
Строка, в том числе `"1.0"`, bool, список/объект и nonfinite number недопустимы.

`_score` документа продолжает валидироваться своим существующим владельцем.
В этой правке не вводится проверка равенства `_score` и `sort[1]`, пересортировка,
восстановление пропущенного ключа или проверка tier по конфигурационной карте.
Ключ типа `0.0` допустим: JSON number из script sort не обязан декодироваться как int.

### 6.2. Область действия и отказ

Строгая тройка относится к уже поддержанному C3 sort, а не к новому универсальному
протоколу сортировки. Ответ без sort-запроса сохраняет существующее поведение
generic sort evidence; при отсутствии `hit.sort` сохраняется `[]`.
Не следует чинить несвязанные особенности обычного OpenSearch search.

Пустая успешная выдача допустима: отсутствие hits не является отсутствием
обязательных ключей у документа. Непустая выдача без корректного `hit.sort`
отклоняется полностью. Повреждение последнего hit не должно публиковать первые hits.

## 7. R4 — server timing

| Ответ | Результат |
| --- | --- |
| Ключ `took` отсутствует | `server_took_ms=None` |
| `took=0` или другое неотрицательное целое | Значение сохранено без преобразования |
| `took=null`, bool, строка, float (включая `1.0`), отрицательное число, массив/объект | Ошибка валидации research response |

Наличие ключа проверяется отдельно от его значения. Client elapsed time не
подставляется вместо отсутствующего server timing. Проверка действует также
при пустом массиве hits. Client timing и его существующая проверка не меняются.

## 8. Failure semantics и совместимость

R1/R2 исправляют локальную diagnostics, не меняя правила допуска вакансий.
Missing source data не становится ошибкой поиска и не превращается в доказательство
missing doc values. Ошибки R3/R4 означают malformed response, а не пустую выдачу.

Для R3/R4 обязателен следующий путь:

1. `observe` отклоняет некорректный ответ до возврата результата.
2. `ResearchSearchTransformer` сохраняет исходные items, context, filters и branches.
3. Compare/batch останавливается; последующие поиски не вызываются.
4. Exporters не вызываются, нового research artifact на диске нет, существующий
   файл остаётся побайтно прежним. Уже выполненные read-only HTTP не откатываются.
5. Ручной пользователь может повторить поиск с тем же экземпляром после исправления
   ответа; не возникает отравленного «последнего результата» или накопленных flags.

Прямой вызов boundary сообщает `ValueError`; транспортные ошибки, включая неверный
JSON/nonfinite JSON, сохраняют существующую классификацию. Не нужен общий catch,
который смешивает эти ошибки или возвращает фиктивную успешную SERP.
CLI сохраняет безопасный тип/фазу ошибки и exit code 1, без сырого ответа и credentials.

Public signatures, `schema_version=1`, набор ключей metadata и существующие имена
flags сохраняются. Меняются ошибочные значения diagnostics и приём некорректного
research response. Старые файлы не переписываются; сравнение старого/нового запуска
должно учитывать исправление diagnostics. Прежние searches.json/comparison.json/CSV,
Hydra defaults, dependencies и lockfile не требуют изменения.

## 9. Acceptance matrix

| ID | Существенный сценарий | Доказательство |
| --- | --- | --- |
| A1 | Плоские и вложенные пути, глубина >1, literal dotted key и коллизия | Точное value/flags по R1, независимость snapshot |
| A2 | Missing/null, `0`, промежуточный scalar/массив, отсутствующий `.keyword` | Нет ложной подстановки, coercion, обхода массивов или изменения fields |
| A3 | ISO/epoch int/epoch float: прошлое, равенство, будущее; timezone offsets | Точный `future_source_date`, одна и та же fixed session time |
| A4 | Дата без timezone, invalid string, bool | Прежние flags сохранены; нет bool-as-number и догадок о времени |
| A5 | Balanced и single-signal profiles | Проверяются только активные роли; C1/C4/C5 не требуют ranking metadata |
| A6 | C3 score sort: int/float/null против string/bool/container/nonfinite | Валидные ключи сохранены, невалидные отвергнуты владельцем boundary |
| A7 | Missing/invalid took, 0, positive int, пустая выдача | Точная семантика R4 независимо от числа hits |
| A8 | Корректный первый hit, повреждённый второй | Отказ всей выдачи, исходный payload не изменён |
| A9 | Первый поиск успешен, второй повреждён, третий подготовлен | Третьего HTTP нет, exporters не вызваны, новый файл не опубликован |
| A10 | Существующий файл и отказ A9 | Его байты не изменились; ошибка не скрыта успешным экспортом |
| A11 | Повторный ручной вызов после ошибки | Успешная независимая SERP без старой diagnostics |
| A12 | Preview и реальные исходящие bodies | Исправления evidence не меняют отправленный DSL, hard filters или ranking params |

Параметризованные unit/contract checks покрывают таблицы R1–R4. Для A6 nonfinite
нужно различать прямой вызов конвертера и JSON-ответ через HTTP: второй может
законно отклоняться раньше на транспортной границе.

Минимальный составной positive path: существующая Hydra-композиция C2 с вложенными
ranking-полями → локальный HTTP → аномальная numeric date/negative quality →
research JSON, с полными неизменёнными fields и корректными metadata. Дополнительно
проверить C3 finite/null score keys и optional missing took в успешном результате.

Минимальный составной negative path: параметризовать повреждение второго ответа
между строковым C3 score key и явным `took:null`, проверить остановку, payload и export.
Использовать существующие HTTP fixtures и настоящие experiment/export paths;
spy допустим для доказательства отсутствия вызова exporter, но не вместо всего пути.

Не требуется декартово произведение всех дат, всех profiles и всех ошибок.
Проверки должны различать контракты и owners, а не повторять внутренние ветви кода.

## 10. Ближайший этап исполнения

Этап один: исправить research evidence без изменения поиска. Он включает R1–R4;
его exit evidence — acceptance matrix и локальные gates. Разделение ниже —
рабочий task plan, а не новая архитектура или отдельные продуктовые milestones.

| Шаг | Действие | Проверяемый результат |
| --- | --- | --- |
| 1 | Проверить branch/status, актуальный diff и owners относительно baseline; перенести воспроизведения R1–R4 в contract tests | Подтверждены именно текущие дефекты; существующий null score остаётся положительным case |
| 2 | Исправить source lookup и сравнение дат в owner diagnostics | A1–A5 проходят, source/params не мутируют |
| 3 | Исправить проверку sort score и presence-aware took в owner evidence | A6–A8 проходят; неправильный ответ не создаёт SERP |
| 4 | Закрыть составные positive/negative paths и повторный вызов | A9–A12 проходят, ошибка не публикует частичный результат |
| 5 | Синхронизировать canonical docs с реализованным контрактом | Архитектура описывает актуальные правила; development содержит реальные результаты и ограничения |
| 6 | Запустить gates, проверить final diff и сделать handoff | Исправления обозримы; локальная и внешняя готовность явно разделены |

Ожидаемые затрагиваемые места: два owner-модуля из раздела 3,
существующая research test suite и документация. Это ориентир, а не требование
создать файлы/abstractions или менять reporting/transport ради удобства доступа.

В `architecture.md` после реализации кратко закрепляются source path precedence,
numeric date units, типы sort keys и missing/invalid timing со ссылкой на эту spec.
В `development.md` фиксируются закрытие R1–R4, команды, результаты и непроверенные
границы. README дополняется только необходимыми пользователю пояснениями о
source fields/date units, если без них настройка неоднозначна. Терминология
`CONTEXT.md` не меняется: новых доменных понятий здесь нет.
Исторический аудит не переписывается в «успешный»: закрытие ссылается на новое evidence.

### Локальные команды

Сначала — узкая изменённая suite:

```sh
poetry run pytest tests/test_research_ranking.py
```

Затем обязательные gates:

```sh
poetry run ruff check .
poetry run ruff format --check .
poetry run ty check
poetry run pytest
git diff --check
```

Проверить локальные Markdown targets и отсутствие случайных notebook outputs.
Если Poetry недоступен, разрешён существующий `.venv/bin` по правилам spec 006
с явным указанием, что installation/lock verification не выполнены.
Не повторять тяжёлую матрицу previews без новых изменений query/config или
неразрешённого риска: R1–R4 изменяют обработку результата, а не compiler.

### Локальное завершение

- R1–R4 и A1–A12 имеют evidence; обязательные gates пройдены либо точное
  ограничение среды явно записано без объявления пропущенной проверки успешной.
- Сохранены contracts specs 001–006, no-overwrite и отсутствие partial mutation/export.
- Нет новых dependencies, runtime modes, secrets или несвязанных изменений.
- Статус spec переведён в «реализована локально», development обновлён.
- Указаны оставшиеся внешние проверки. Их отсутствие не маскирует успех/неуспех
  локальных исправлений и не требует установки OpenSearch на текущем VPS.

## 11. Внешняя приёмка переноса — отдельный результат

Это план закрытия verification gaps аудита, а не скрытая дополнительная разработка
и не условие локального завершения R1–R4. Исполнение зависит от целевого окружения
и разрешённых данных. До получения evidence статус — «не проверено».

| Область | Входные данные | Действие и exit evidence |
| --- | --- | --- |
| Установка | Целевая ОС, Python, Poetry, checkout | `poetry check --lock`, чистая `poetry install`, CLI import/run и проектный notebook kernel; записаны версии/команды/исход |
| Подключение | Разрешённый URL/auth, index и известный запрос | Только search: успешный ответ с полными fields; auth не включён в опубликованные конфиги/логи |
| Source profile | Версия сервера, text fields/analyzers, ranking field types/doc values и single-valued guarantees | Фактические поля сопоставлены декларациям; нет предположения, что имя поля доказывает mapping |
| C2 и используемые абляции | Разрешённые score/rescore contexts, реальные date/quality | Painless исполняется; используемые combined/single-signal/rescore режимы отдельно проверены; metadata соответствуют возвращённому source |
| C3 | Категории и уникальный stable id с doc values | Наблюдается согласованный tier order, lexical score и stable tie-break; sort evidence читается корректно |
| C4/C5 | Разрешённые контрольные запросы/вакансии | Проверены aliases, квалификации, отрицания и rewrite на реальном analyzer; ошибки не превращаются в fallback |
| Артефакты | Одиночный запрос и небольшой CSV | JSON/CSV содержат полные результаты и успешную пустую выдачу; повторная публикация не перезаписывает файл |
| Качество/latency, если выбирается рабочее ranking | Разметка, запросы и согласованный приемлемый результат | Отдельное продуктовое решение; синтетические тесты/перестановки сами по себе не доказывают улучшение |

Полный live smoke нужен только для вариантов, выбранных к использованию; проверка
C1 не распространяется на C2/C3. Если cluster запрещает script context, зафиксировать
ограничение: не менять настройки и не объявлять вариант совместимым через fallback.
Отсутствие административного доступа не разрешает вызывать недоступные API:
mapping/версия могут быть предоставлены владельцем контура, приложение использует search.

Перед установкой/созданием окружения оценить диск по AGENTS.md. На текущем VPS
аудит наблюдал 94% заполнения; новая тяжёлая установка не подразумевается этой spec.
Не коммитить credentials, реальные персональные документы, resolved secret-bearing
configs или private artifacts ради evidence. Результат внешней проверки может
содержать безопасное резюме и ссылку на разрешённое хранилище артефактов.

Остающиеся внешние входы: целевая машина, профиль индекса, допустимые варианты,
разрешённые запросы и критерии продуктовой приёмки. Они не нужны для локального
исправления четырёх дефектов и не должны заменяться выдуманными значениями.
