## Замысел системы

Проект — среда для написания и запуска экспериментов над поиском и обработкой
документов. В ней эксперимент задаёт конкретный сценарий работы, а переиспользуемые
части сценария имеют явные интерфейсы и собираются конфигурацией. Первый сценарий
предельно практический: человек вводит запрос, получает вакансии и рассматривает
выдачу. В дальнейшем эксперименты могут решать другие задачи, но сейчас они
не являются основанием добавлять новые режимы или инфраструктуру.

Свобода написания экспериментов означает, что сценарий остаётся обычным Python-кодом:
он может содержать цикл ввода, вызовы обработки, работу с результатом. При этом
логика поиска, представление документов и преобразования данных не должны
растворяться в теле одного CLI-скрипта. Для них уже намечены отдельные понятия.

DDD здесь означает прежде всего согласованный язык и владельцев поведения.
Вакансия, фильтр, выдача и результат эксперимента имеют собственный смысл,
который сохраняется при изменении транспорта или терминального представления.
Само требование DDD не предписывает добавлять repositories, services, aggregates
или другие слои, для которых ещё нет задачи.

Путь OpenSearch работает поверх внешнего индекса: приложение управляет обработкой
и вызовами поиска, но не владеет его состоянием. Поэтому одинаковые входы
не гарантируют одинаковой выдачи в разные моменты времени. Векторный путь создаёт
собственные исследовательские поколения коллекций в предоставленном пользователем
Qdrant. Приложение владеет их построением и публикацией; процесс Qdrant и его
хранилище остаются у оператора. Готовое поколение приложение больше не изменяет.

## Три уровня композиции

| Уровень | Что задаёт | Пример первого сценария |
| --- | --- | --- |
| Эксперимент | Сценарий исполнения и работу с его результатом | Интерактивная сессия внутри `run` |
| Pipeline из transformers | Обработку одного состояния данных | Из условий поиска получить документы |
| Интеграция | Взаимодействие с внешним источником | Вызов `search` у прокси OpenSearch |

Hydra задаёт конфигурацию объектов и их связей на этих уровнях. Registry даёт
transformers имена, по которым композиция может на них ссылаться. `PipelineData`
переносит состояние конкретной обработки. Это разные роли: конфигурация описывает,
чем и как обрабатывать данные, а payload содержит сами данные текущего выполнения.

Например, поля поиска и параметры базового DSL относятся к конфигурации.
Введённая строка относится к входу текущего поиска и выражается `QueryFilter`.
Полученные вакансии становятся items результата. Перенос всех этих значений
в один произвольный словарь сделал бы их владельцев неразличимыми.

## Pipeline и registry

Registry transformers связывает имена с transformers. Pipeline задаётся явной композицией
transformers через конфигурацию; сам pipeline также выражается transformer.
Ветвления и объединение обработки выражаются transformers, а не отдельным
языком orchestration. Общий контейнер данных позволяет поддерживать такие ветвления.

Последовательные шаги получают результат предыдущего шага. Registry не выводит
маршрут автоматически из типов входа и выхода. Hydra собирает объекты и связывает
их конфигурацией и интерполяциями.

Сохранены `BaseRegistry`, `SimpleRegistry`, `BaseTransformerRegistry` и
`BasicTransformerRegistry`. Общий registry задаёт lookup по имени, SimpleRegistry
хранит готовые объекты. BasicTransformerRegistry специализирует его для transformers
и проверяет ссылки и циклы pipelines и ветвлений при создании.
Старый отдельный registry компонентов не считается автоматически принятым
требованием новой архитектуры.

Общий `BaseRegistry` и специализированный registry transformers не следует
считать синонимами: первый задаёт общий механизм, второй — его роль в композиции
обработки. Registry передаётся в `transform` явно; leaf transformers получают
интеграцию в конструкторе. Lookup переиспользует экземпляр, а не создаёт новый.

### Registry: именованные преобразования

Registry позволяет описывать состав эксперимента через имена объектов.
Содержательный смысл имени определяется конкретной конфигурацией: например,
`search` может обозначать transformer поиска, а `search_pipeline` — композицию,
включающую этот transformer. Pipeline обращается к зарегистрированным объектам,
а не создаёт свою реализацию поиска внутри каждого шага.

Это даёт возможность менять состав обработки в конфигурации, оставляя механизм
исполнения одинаковым. Сам registry не является хранилищем результатов запросов,
алгоритмом ранжирования или планировщиком поиска пути между типами.

### Transformer: единица обработки и композиции

Transformer получает обобщённое состояние обработки и возвращает состояние
для дальнейшей работы. Концептуальная форма контракта —
`transform(data, *, registry) -> PipelineData`. Общий registry позволяет составному
шагу разрешать имена без глобального состояния и циклического связывания объектов.

Обычный transformer выполняет конкретное действие над данными. Композиционный
transformer управляет вызовами других transformers: последовательно, условно
или по веткам. Поэтому pipeline можно использовать там же, где отдельный шаг.
Эксперименту не нужно знать все внутренние шаги составного преобразования.

Transformer не обязан быть математически чистой функцией: разрешено изменение
переданного состояния, а поисковый путь включает внешний вызов. Но общее имя
`transformer` не переносит ответственность за сетевой протокол из интеграции.

### Явная последовательность и вложенность

Ниже иллюстрация композиции по именам. Имена и запись условные; это не готовый
Hydra YAML и не требование реализовать именно эти классы:

```text
registry:
  search          → transformer поисковой обработки
  search_pipeline → pipeline с шагами [search]

эксперимент → registry[search_pipeline] → registry[search]
```

Если позднее понадобится ещё один шаг, конфигурация pipeline сможет явно
перечислить его после поиска. Если понадобится вложенный pipeline, его имя
можно будет использовать как имя составного шага. Наличие такой модели не
требует добавлять пустые шаги в первый эксперимент ради демонстрации гибкости.

## PipelineData

`PipelineData` — обобщённое состояние обработки с тремя содержательными частями:

| Часть | Контракт |
| --- | --- |
| Контекст пользователя | Key-value данные пользователя |
| Items | Документы — наследники `BaseDocument` |
| Фильтры | Условия — наследники `BaseFilter`, включая `QueryFilter` |

Строгие типы документов и фильтров сочетаются с общим контейнером. Для каждого
шага не требуется отдельный несовместимый тип pipeline payload. Поля называются
`context`, `items`, `filters`. Items содержит коллекцию документов. Отдельное
временное поле `branches: dict[str, PipelineData]` хранит результаты веток;
оно не является частью пользовательского контекста.

Transformer может изменять `PipelineData` и явно создавать его копии.
Автоматическое копирование перед каждым шагом не требуется.

### Зачем нужен общий контейнер

`PipelineData` представляет состояние обработки, а не только ответ поиска.
Перед поиском в нём могут быть контекст пользователя и фильтры; после поиска
появляются найденные items. Шаги работают с нужной им частью состояния, сохраняя
возможность дальнейшей композиции.

Общий контейнер нужен в том числе для ветвлений. У разных веток могут различаться
применённые преобразования и полученные items, но у них остаётся общий способ
принимать и возвращать состояние. Замена этой модели цепочкой несовместимых
payload-классов для каждой стадии изменила бы согласованный принцип композиции.

Обобщённость не означает, что внутри всё становится `Any`. Документы остаются
наследниками `BaseDocument`, фильтры — наследниками `BaseFilter`. Для контекста
выбрана форма `dict[str, JSONValue]`, совместимая с JSON и копированием. Произвольные ресурсы, клиенты и registry не являются пользовательским
контекстом только потому, что их удобно положить в словарь.

### Контекст, фильтры и запрос

Контекст описывает пользователя. Фильтр выражает условие обработки.
Например, свойство пользователя и условие поиска, построенное на его основе,
могут быть связаны, но это разные роли данных. `TermFilter` хранит поле и scalar
значение. `UserPropertyFilter` хранит поле индекса и имя свойства контекста;
поисковый transformer разрешает это свойство перед внешним вызовом.

Введённый текст хранится в `QueryFilter`. Его не следует одновременно дублировать
в `context["query"]` как второй источник истины. Имя «фильтр» здесь шире, чем
OpenSearch `bool.filter`: текстовый фильтр может определять полнотекстовую часть
DSL и влиять на score. Наследование от `BaseFilter` не означает механического
помещения любого такого объекта в одноимённую секцию DSL.

`Request` наследует `BaseRequest` и фиксирует immutable snapshot фильтров одного
поиска. Transformer строит его из payload, затем преобразует условия в DSL.
Аргумент интеграции — уже готовый DSL; пользовательский контекст и результаты
не являются частью Request.

### Фильтры и копирование

Набор фильтров допускает только добавление. Уже добавленный фильтр нельзя удалить,
заменить или изменить; неизменяемость распространяется на вложенные значения.
Это правило действует и для `QueryFilter`.

При копировании контейнер фильтров независим, а неизменяемые экземпляры фильтров
могут оставаться общими. Добавление фильтра в одной копии не меняет другую.
Разрешение менять `PipelineData` не отменяет ограничений на фильтры.

Историческая реализация в `change/structural-search:src/models/core.py` и
`master:src/ranking/execution/model.py` имела поверхностный `copy()` и
`copy(deep=True)`. Transformer ветвления использовал глубокую копию для каждой
ветки; экземпляры фильтров оставались общими. Это ориентир для разработки,
а не готовая реализация нового контракта: старый механизм копировал документы
как словари и не поддерживал произвольных наследников `BaseDocument`.
В новой реализации сохранены `copy()` и `copy(deep=True)`. Первая создаёт новые
внешние контейнеры, вторая использует стандартный `deepcopy` контекста и коллекции,
поддерживающий доменные dataclasses. Фильтры остаются общими immutable values.

### Пример изменения и ветвления

Пусть исходное состояние содержит фильтр `QueryFilter` с текстом «python».
Transformer может дополнить его набор новым фильтром. Он не может переписать
исходный текст на «java», удалить исходный фильтр или заменить весь набор так,
чтобы исходное условие исчезло.

Для двух независимых веток состояние можно скопировать:

```text
исходные данные: context, items, filters=[Q]
                    |
           transformer ветвления
               /           \
         копия A           копия B
       filters=[Q,A]     filters=[Q,B]
               \           /
          результат ветвления
```

Здесь `Q` — один неизменяемый фильтр, который допустимо разделять. Контейнеры
фильтров независимы: добавление `A` не добавляет его в ветку B или исходное
состояние. Поверхностная копия документов при этом сама по себе не даёт
изоляции их вложенных данных. Независимость веток требует подходящей семантики
копирования именно тех данных, которые ветки изменяют.

`BranchTransformer` разрешает все имена и готовит независимые deep copies до
первого вызова. Ветки выполняются последовательно; их результаты публикуются
в `branches` только после успеха всех веток. Повторное ветвление при непустом
workspace запрещено. Вложенная ветка должна объединить собственные результаты
перед возвратом. Shallow copy копирует внешний mapping веток, deep copy — каждую
ветку рекурсивно, сохраняя общие immutable filters.

`ReciprocalRankFusionTransformer` объединяет выдачи по id, суммируя
`1 / (rank_constant + rank)`, где rank начинается с 1. При совпадении id поля
берутся из первого появления; результат — отдельные документы с RRF score.
Равные scores сохраняют порядок первого появления. Duplicate id внутри ветки
отклоняется. После успеха workspace очищается, parent filters не меняются;
добавленные фильтры веток остаются локальными. CLI не требует ветвления.

`FieldScoreExtractor` переносит числовое поле документа в score после проверки
всей коллекции. `TopKTransformer` оставляет первые k документов без сортировки.

Правила конфликтов принадлежат преобразованию. Первый OpenSearch transformer
требует ровно один QueryFilter. Term-условия соединяются AND без дедупликации;
неизвестные фильтры и отсутствующие свойства пользователя вызывают ошибку до
поиска. Уже добавленное условие не перезаписывается другим.

## Документы и SERP

Доменные документы наследуют `BaseDocument`; первый конкретный тип — `Vacancy`.
Внешние представления преобразуются в доменные через предусмотренные в каркасе
абстракции внешних документов и коллекций.

SERP — упорядоченный набор items. Поисковый путь сохраняет все поля возвращённых
вакансий и score; преобразование и терминальное представление не должны
необратимо отбрасывать поля ради фиксированного краткого набора.

В PipelineData поле items содержит коллекцию, в поисковом результате — SERP.
Документ хранит `id`, `fields` и `score` конкретного попадания в выдачу. Терминал
показывает полный JSON. Технический ответ доступен в OpenSearchResult.response,
но в поисковый артефакт попадают документы, а не весь response.

### Документ, внешний документ и результат поиска

`BaseDocument` задаёт принадлежность к доменным items. `Vacancy` — конкретный
вид такого item. `BaseExternalDocument` и `BaseOpenSearchDocument` представляют
внешнюю форму данных; `VacancyOpenSearchDocument` преобразует эту
форму в доменную вакансию. OpenSearchResult преобразуется в SERP через контракт
внешней коллекции.

Граница преобразования нужна, чтобы остальная обработка оперировала документами,
а не разбирала OpenSearch hits в каждом месте. При этом преобразование не должно
обеднять данные: если источник вернул описание или дополнительные поля вакансии,
их нельзя потерять из-за того, что терминальная карточка показывает лишь название.
Все поля источника сохраняются внутри `fields`, без фиксированного списка атрибутов.

SERP несёт порядок items. Перестановка элементов меняет выдачу, даже если набор
идентификаторов остался тем же. Score относится к появлению документа в данном
поиске: одна вакансия может получить разные значения при разных запросах.
Поэтому экземпляр документа относится к конкретному поиску и не кэшируется глобально.

Терминальное отображение — представление результата. Оно может организовывать
поля для удобства чтения, но не должно становиться единственной обеднённой
моделью данных. В первой реализации используется полный JSON-вывод с отступами.

## Поиск и интеграция

Основной источник кандидатов — OpenSearch за прокси. Доступна только операция
`search` с полной поддержкой OpenSearch DSL. Первый эксперимент строит базовый
DSL из текстового запроса, переданного в `QueryFilter`.

Смысловой путь обработки:

```text
ввод текста → QueryFilter в PipelineData → transformers → OpenSearch DSL
→ integration.search → преобразование найденных документов → SERP → терминал
```

Это описание потока данных, а не обязательное число классов или шагов.
Transformers выражают обработку, интеграция владеет взаимодействием с внешней
системой. OpenSearchTransformer строит DSL, вызывает integration.search, полностью
преобразует ответ и только после успеха присваивает новые items.

Полная поддержка DSL описывает возможности внешней операции, а не необходимость
сразу создавать собственный язык для всех вариантов запросов. Первый pipeline
использует базовый поиск; его конкретные поля и параметры будут конфигурацией.
Текст пользователя остаётся данными этого запроса, а не готовым DSL из терминала.

Доступность `search` не даёт оснований рассчитывать на создание индексов,
индексацию документов или административные методы. Пользователь подтвердил:
формат запроса и ответа полностью соответствует настоящему OpenSearch;
URL и авторизация параметризованы. Конкретные значения подключения задаются
конфигурацией; транспорт использует urllib и только POST search. Технический
контракт описан в [spec 001](specs/001-interactive-search.md).

## Hydra и расположение реализаций

### Модульный jobboard-поиск

`JobSearchTransformer` в `core/transformers/opensearch/jobboard` использует прежний
`OpenSearchIntegration`; транспорт и общий `OpenSearchTransformer` остаются владельцами
своих прежних контрактов. Его путь: snapshot Request → parser → чистый compiler →
HTTP → полная конвертация → замена items. Ошибки до HTTP не меняют payload;
ошибка ответа не публикует частичную SERP.

`domain/request/jobboard.py` хранит неизменяемые QueryHint и ParsedQuery. Последний
существует только внутри вызова и не записывается в context, filters или branches.
Нормализация принадлежит `components/query/normalization.py`; независимые стадии
разбора и их композиция — `components/query/jobboard`. Каждая стадия читает один
нормализованный текст. Один LexiconQueryStage обслуживает разные категории данных;
новый алгоритм может реализовать BaseQueryStage. Словари читаются Hydra при сборке,
а не через файловый ввод-вывод внутри parse.

SourceProfile декларирует text-поля, optional title и типы разрешённых term-полей;
он не инспектирует удалённый mapping. LexicalQueryConfig управляет весами, покрытием,
aliases, phrase, мягкими атрибутами, topical gate и бюджетами. Все явные filters
сохраняют AND-семантику; неизвестная capability или несовместимый scalar отвергаются.
Распознанные место, уровень и формат работы не создают новых жёстких filters.

Compiler объединяет literal и concept paths через dis_max с нулевым tie breaker.
Группы понятий допускают курируемые альтернативы; остаточный текст сохраняется.
Обязательное lexical evidence и общий нулевой по score topical gate отделены от
добавочных boosts: совпадение одних атрибутов не заменяет подтверждённую профессию
или навык. Неоднозначные сокращения не расширяются. Неподдержанная связка/отрицание
отключает structured и fuzzy paths всего запроса; whitelist полных фраз вроде
«без опыта» задаётся явно. Это не обещание понимания произвольной логики.

Fuzzy — отдельно выбираемый ограниченный путь допуска кандидатов. Он применим к
неизвестным длинным буквенным tokens, с сохранением остальных anchors. Fused получает
полную глубину двух leaf-поисков, затем существующие RRF и TopK. Промежуточные
конечные pipelines, уже обрезанные до final_k, в fusion не используются.

Конфигурации находятся в `configs/jobboard/lexical`, wrappers — в отдельной папке
`configs/experiments/vacancy-search/jobboard/lexical`. Main default и общий payload
не зависят от этого эксперимента. Synthetic cases задают полную разметку замкнутого
вымышленного корпуса; неизвестный id по-прежнему означает missing judgment.

### Общие правила композиции

Python-код определяет поведение transformers, интеграций и экспериментов.
Hydra выбирает реализации, задаёт параметры и связывает составные конфигурации.
Интерполяции позволяют ссылаться на уже описанные части конфигурации вместо
повторения настроек каждого вложенного объекта.

Интерполяция конфигурации сама по себе не устанавливает Python identity или
lifecycle объекта. Entry point один раз создаёт эксперимент и вложенные
зависимости через instantiate; registry хранит полученные экземпляры. Интеграция
закрывает каждый HTTP response после чтения, открытого клиентского lifecycle нет.

Весь код находится в `src/`, включая узкие конкретные реализации для эксперимента.
Конфиги организуются вложенно по задаче и варианту, например
`configs/experiments/vacancy-ranking/task-1/001-baseline`. Этот путь показывает
принцип организации. Рабочий CLI-конфиг находится в
`configs/experiments/vacancy-search/interactive/001-basic.yaml`.

## Эксперимент и сохранение

`SearchExperiment.search(text, *, context=None, filters=())` выполняет один поиск
без терминального ввода, печати и экспорта. Он владеет созданием независимого
payload, применением статического контекста и условий, добавлением QueryFilter
и проверкой завершённой SERP. Контекст вызова переопределяет свойства верхнего
уровня; дополнительные filters только добавляются к статическим. Возвращается
глубокий снимок SERP. Пустой текст и QueryFilter среди дополнительных условий
отвергаются до pipeline. `run()` использует этот же метод для терминальной сессии.

Ноутбук собирает обычные объекты через Hydra Compose API; exporters отключаются
или получают явный путь вместо зависимости от CLI runtime. Изменение конфига
требует новой instantiate. Оба поисковых leaf transformer имеют `build_query(data)`:
он строит тот же DSL, что использует transform, без HTTP и изменения payload.
Это интерфейс отдельного поискового листа, а не второй исполнитель графа.

`BatchSearchExperiment` получает настроенный SearchExperiment и путь к CSV-набору.
Его `run()` читает и структурно проверяет весь набор до первого поиска, затем
последовательно вызывает `search()` и возвращает BatchSearchArtifact. Метрики и
judgments не требуются. Невалидный запрос на стадии parser/compiler или ошибка
HTTP прекращают обработку без экспорта; предыдущие HTTP не откатываются.
Артефакт хранит независимые снимки, id/текст запросов и полные SERP, предоставляет
JSON и табличное представление. SearchCSVExporter сериализует таблицу и публикует
один CSV атомарно, без overwrite, общим с JSONExporter механизмом. Пустая выдача
имеет отдельную строку. Точный CSV contract принадлежит spec 005.

Дополнительный `CompareExperiment` обрабатывает `ComparisonCase` независимой
копией для каждого именованного pipeline. Case задаёт ключ, входной PipelineData
и явные оценки релевантности по id. Результатом каждого pipeline должен быть
SERP без необъединённых веток. NDCG не использует поисковый score как разметку:
идеальная выдача строится по всем judgments, неизвестный grade оцениваемого
документа является ошибкой. `ComparisonArtifact` хранит снимки полных выдач,
отчётов метрик и описательную статистику по каждой паре pipeline/metric.
Ошибка прекращает эксперимент без экспорта. Сравнение не выбирает победителя.

В поисковом сценарии Hydra запускает один комплексный эксперимент. Его `run` владеет интерактивной
сессией: пользователь последовательно вводит запросы и видит SERP в терминале.
На этом этапе оценка выдачи выполняется глазами.

По завершении результат сохраняется через артефакт эксперимента. В текущем
коде `BaseArtifact` владеет представлением результата, `BaseExporter` — внешней
записью. `_wrapped_run` вызывает exporters после успешного `run`. SearchArtifact
хранит снимки запросов и выдач; JSONExporter атомарно публикует один JSON-файл.
Терминальное отображение происходит во время сессии, а не только после `run`.
Оба эксперимента принимают только завершённую SERP без необъединённых веток.
Иная коллекция или непустой workspace — ошибка до отображения выдачи и экспорта.

При ошибке выполнение аккуратно логируется и завершается. Продолжение сессии
после ошибки не является выбранным поведением. Неполный ответ — ошибка. EOF
сохраняет артефакт и завершает с кодом 0; ошибка и Ctrl-C не сохраняют артефакт
и дают коды 1 и 130. Ранее показанные результаты остаются в терминале.

Воспроизводимость зависит от эксперимента и источника данных: проект работает
как обёртка над ними. Обязательные снимки индекса, документов или всей сессии
для каждого эксперимента не вводятся.

### Сквозной пример сессии

Ниже последовательность наблюдаемого поведения, а не готовый API:

1. Запуск через Hydra выбирает и собирает конфигурацию эксперимента и обработки.
2. `run` начинает интерактивную сессию и получает строку, например «python».
3. Строка представляется как `QueryFilter` во входных данных обработки.
4. Эксперимент запускает сконфигурированную композицию transformers через registry.
5. Поисковый путь формирует DSL и вызывает `search` интеграции.
6. Внешние документы преобразуются в items; выдача сохраняет их порядок, поля
   и score. Пользователь видит результат в терминале.
7. Сессия принимает следующий запрос либо завершается. Следующий ввод является
   новым поиском; накопление текстовых запросов как условий одного поиска
   не следует из append-only правила фильтров.
8. Результат эксперимента передаётся в механизм сохранения через артефакт.

Таким образом, один вызов `run` охватывает несколько поисков. Pipeline выполняет
обработку, а интерактивный цикл принадлежит эксперименту. Каждый ввод создаёт
новый payload с копией исходного контекста, статическими фильтрами и новым
QueryFilter. Между вводами сохраняются только снимки результатов для артефакта.

`BaseExperiment.run() -> BaseArtifact`, `_wrapped_run` и `BaseExporter.export`
разделяют сценарий, результат и сохранение. Экспорт автоматически вызывается
из `_wrapped_run` после успеха; сам артефакт файловый I/O не выполняет.

При ошибке поиск не подменяется пустой успешной выдачей. Принятое поведение —
логирование и выход без частичного артефакта. Успешный поиск без найденных документов и ошибка поиска —
разные исходы, которые нельзя смешивать в одном неразличимом результате.

## Исследовательские кандидаты 006

Новый профиль `blue-collar/ru` собирается через Hydra-фабрику `research_registry`.
Она создаёт обычные именованные `ResearchSearchTransformer`, разделяющие source,
parser, HTTP-клиент и фиксированное время сессии. `selected` ограничивает сборку:
выбор C1/C4/C5 не требует отсутствующих ranking metadata. Никакого нового registry
протокола нет. Query и ranking — типизированные конфигурационные значения;
Painless source/params принадлежат YAML в `configs/jobboard/lexical/ranking`.

`SlotQueryParser` наследует существующий ModularQueryParser с opt-in правилами
вложенных профессий, вводных фраз и диагностикой. Нормализация и LexiconQueryStage
переиспользованы. Дополнительные kinds — experience/schedule/employment/qualification/
work_condition — не меняют старые наборы стадий. Полные роли подавляют вложенный
общий role/skill; diagnostics сохраняют причину. Bare обозначения категорий имеют
явные surface-prefix rules, чтобы русские предлоги «в»/«с» не превращались в права B/C.

Концептуальный compiler маршрутизирует role/skill/attributes по полям. Квалификация
обязательна внутри structured path, мягкие атрибуты не удовлетворяют тематическую
coverage. Literal path сохраняется с собственной eligibility; это не юридическая
проверка квалификаций всех результатов. Неизвестный residual не удаляется, кроме
конечного списка вводных фраз. Числа и графики сохраняются атомарно; зарплата пока
не преобразуется в диапазон filters.

`ConservativeRewriter` строит независимые curated/layout/spelling proposals по
локальному recognition vocabulary. Подтверждение цели выполняет тот же parser
по полному изменённому запросу; phrase spans и контекст имеют значение. Все каналы
проверяются до выбора: разные concepts у любого span отменяют весь rewrite.
При одном concept форма выбирается детерминированно. Максимум две замены дают одну
новую строку без каскада. Original и rewritten компилируются как две dis_max ветки
одного search с общими внешними filters; исходный Request не изменяется.

`RankingConfig` применяет один mode к готовому body: relevance, script_score,
script_sort либо phrase_rescore. Активные field bindings проверяются по декларациям
source до HTTP; отключённые сигналы имеют отдельные source без обращений к их полям.
Custom sort и rescore не совмещаются. Время фиксируется на сессию, а не читается
скриптом. Локальная проверка source/params не компилирует Painless.

Локальная ranking diagnostics читает только активные source fields: точный
верхнеуровневый ключ имеет приоритет, включая явный null; иначе имя с точками
разрешается через вложенные JSON-объекты. Массивы и mapping aliases не обходятся,
суффикс `.keyword` не удаляется. Missing/null сохраняет `missing_source_<role>`;
это не доказательство отсутствия doc values. Values сохраняют исходный JSON-тип
и независимый snapshot. Числовая дата — epoch milliseconds (не bool), будущая дата
строго больше фиксированного `now_ms`. ISO-дата с timezone сравнивается как момент
времени; без timezone и при неразбираемой строке сохраняются прежние flags.

`ResearchSearchTransformer.plan` — общий compiler для preview и transform.
После полного успешного HTTP и преобразования создаётся `ObservedSERP` — SERP
с отдельными request/understanding/timing/sort metadata. Документы не получают
технических полей в `_source`; user context и глобальное состояние не используются.
Sort values привязаны к id, требуются уникальные документы и корректные ключи C3.
Обычный SearchExperiment.search возвращает независимый deep snapshot этого результата.

В C3 sort keys — конечный numeric tier, конечный numeric score либо null и непустой
строковый stable id; bool и числовые строки не принимаются как числа. `_score`
сохраняется отдельно, клиент не восстанавливает и не пересортировывает ключи.
Отсутствующий `took` даёт `server_took_ms=null`; присутствующий обязан быть
неотрицательным int, не bool, float или null, включая ответ без hits. Повреждение
любого hit/timing отклоняет результат до замены items и экспорта; повторный ручной
вызов остаётся возможным. Точные границы и проверки — в
[spec 007](specs/007-research-evidence-corrections.md).

`ResearchExperiment` использует SearchExperiment для выбранных листьев и проверяет
все входные query plans до первого HTTP в сравнении. `ResearchArtifact` публикует
отдельный `schema_version=1` JSON; прежние searches.json/comparison.json/CSV не меняются.
Ошибка прекращает comparison/batch без экспортируемого частичного результата.
HTML-представление экранирует содержимое документов, полный `_source` доступен отдельно.
Состав обязательного контента и проверок — в [006](specs/006-query-and-painless-candidates.md)
и [006A](specs/006-blue-collar-content.md). Реальный OpenSearch в локальную приёмку не входит.

## Векторный поиск и поколения коллекций 008

Отдельный Hydra root [vector.yaml](../configs/vector.yaml) связывает один embedding
profile, TEI runtime/client, corpus recipe, Qdrant source и эксперимент. `main.yaml`
сохраняет прежний OpenSearch default. Поисковые vector wrappers используют обычные
SearchExperiment, BatchSearchExperiment, registry, PipelineData и TopK; отдельный
VectorIndexExperiment владеет подготовкой поколения. Границы форматов, pinned
версии и критерии приёмки заданы в [spec 008](specs/008-vector-search.md).

### Encoding и идентичность

`EmbeddingProfile` определяет пространство векторов: модель и tokenizer revision,
pooling, normalization, prefixes, длину и правила подготовки текста. `Embedding`
связывает неизменяемые значения вектора с profile id. Canonical JSON и SHA-256
в `domain/serialization` дают общую идентичность profile, recipe и source;
порядок ключей не влияет на hash, а порядок полей recipe влияет.

`VacancyText` выбирает только объявленные верхнеуровневые поля, нормализует каждое
и соединяет их заданным separator. Исходные fields сохраняются отдельно и полностью.
`JSONVacancyReader` проверяет весь непустой массив `{id, fields}` и возвращает
независимый снимок; точные непустые id сохраняются, повторы запрещены.
JSON-boundary отвергает повторные ключи, invalid Unicode, nonfinite numbers и
неподдерживаемые integer values до записи коллекции.

`TextEmbedder` владеет prefix, query/document policy, ограничениями count/bytes и
полной проверкой возвращённого batch: число rows, dimension, finite float32 values
и L2 norm. Query нормализуется без потери регистра, «ё», отрицаний и пунктуации;
document separator после renderer повторно не схлопывается. Query overflow
отклоняется, документ усекается справа средствами pinned tokenizer/runtime.
Клиент не дополняет, не усекает и не перенормирует полученные vectors.

`TEIIntegration` владеет native `/info`, `/health`, `/embed` и `/tokenize`, bounded
HTTP и auth. Перед encoding проверяется совместимость `/info` с profile; ответ
`model_sha` отражает переданный revision и не является независимой аттестацией
weights. Token audit выполняется по одному подготовленному документу с отдельным
response budget. ML runtime и model weights остаются вне Python-приложения.

### Поиск и фильтры

`VectorSearchTransformer.prepare` — чистый план: исходный query, реальный prepared
model input, identities, compiled filters и retrieval parameters. Он не вызывает
inference и не выдумывает vector. TextEmbedder до HTTP проверяет как UTF-8 размер
query input, так и полный JSON body с escaping и flags. `transform` затем проверяет
физическое имя, готовность, descriptor и native schema коллекции через
QdrantIntegration, затем
кодирует один запрос и выполняет один native query. Только после полной проверки
всех points новая обычная SERP заменяет `data.items`. Embedding остаётся локальным
значением шага; context, filters и branches не используются для его передачи.

`QdrantSource` владеет source identity, payload representation, deterministic point
UUID и объявленными filter capabilities. Domain id остаётся в payload рядом с
полными fields; UUID используется только внешним хранилищем.
Материализованная vector schema из Hydra проверяется на совпадение с profile
dimension и Cosine до HTTP; её значения не могут молча расходиться с исполнением.
Каждое разрешённое поле фильтра связывается с явным path и scalar type.
TermFilter и UserPropertyFilter
компилируются в AND; неизвестное поле, отсутствующий context или несовместимое
значение отклоняются до HTTP. Текст запроса не создаёт скрытых фильтров.

Поиск требует совместимых profile, recipe, corpus identity и runtime pins, полного
ready descriptor, ожидаемых payload indexes и одного unnamed Cosine vector.
Alias, building collection и неподтверждённая metadata не являются допустимыми
источниками. Native score, порядок, domain ids и fields сохраняются без пересортировки;
TopK ограничивает итоговую выдачу после candidate retrieval.

### Построение, публикация и отказ

`VectorIndexExperiment` до remote writes проверяет receipt destination, полный
снимок корпуса, ids, payloads, recipe и все encoding batches. Corpus digest
учитывает точные ids и полные fields в стабильном порядке. Версии Qdrant/TEI,
capacity и query/document probes также проверяются до создания коллекции.

Новая физическая коллекция проходит `building → ready`: создание, payload indexes,
последовательные bounded encoding/upload batches с подтверждённым completion,
exact count, полный bounded read-back payloads/vectors и exact filtered smoke.
Публикация заменяет полный descriptor и подтверждается отдельным GET. Существующее
имя не принимается для продолжения или перезаписи; retry/resume/delete отсутствуют.
При сбое до публикации поколение остаётся недоступным поиску; неопределённый исход
PATCH требует чтения remote state. Адресное разрешение состояния принадлежит оператору.

`VectorIndexArtifact` возвращает build receipt существующему JSONExporter после
remote ready. Ошибка локального экспорта завершает запуск с ошибкой, но не отменяет
готовность удалённой коллекции. Search проверяет remote descriptor независимо
от наличия receipt; новый build всегда требует нового имени поколения.

### Владение инфраструктурой и evidence

Узкий TEI launcher читает тот же Hydra profile/runtime, проверяет конфигурацию до
Docker side effect и запускает один pinned container на одном полном GPU UUID.
Он проверяет `/health`, `/info` и query/document probes в пределах общего deadline.
Чтение response body в TEI probes и Qdrant readiness прерывается по deadline,
включая chunk framing; поздний успешный ответ не подтверждает готовность.
Общий владелец этого чтения — `integrations/http_response`; timer отменяется и
завершается до возврата, clients сохраняют ownership auth и native response shape.
DNS и разбор HTTP headers остаются под ограничениями urllib/socket; это не жёсткая
отмена всех OS/network операций. Общий deadline сохраняется между HTTP calls.
Credentials передаются environment; argv не содержит их значений. Launcher не
создаёт Qdrant и не присваивает существующий container. Оператор владеет cache,
storage, адресным restart и разбором оставленного после ошибки состояния.

HTTP readiness и локальные fixtures подтверждают транспорт и orchestration.
Реальные tokenizer boundaries, GPU execution, Qdrant filtering/HNSW, persistence,
качество и capacity требуют отдельных G01–G06 evidence. Актуальные результаты
проверок и незакрытые границы находятся в [development](development.md).

## Исследовательская матрица и notebook 009

[Spec 009](specs/009-search-experiment-matrix.md) задаёт пять fulltext и пять dense
политик. [study.yaml](../configs/study.yaml) собирает только явно зарегистрированные
варианты через `study_experiment`; factory сохраняет существующий
`BasicTransformerRegistry`. По умолчанию зарегистрированы F1–F5; site example
выбирает все десять. Неактивный dense preset не требует URL, image pin или generation.
Parser content и параметры выбранной конфигурации входят в composition fingerprint;
credentials, URL и cache paths исключены до hashing и экспорта.

`StudySearchTransformer` добавляет узкий контракт pure `preview`, `describe` и
remote `admit` существующему transformer. `StudyExperiment` владеет ручным
search/compare и batch preflight. Он создаёт обычный `PipelineData`, разрешает
логические equality bindings в физические source filters и использует
`SearchExperiment` для исполнения выбранных leaves. Static и per-call filters
соединяются AND; следующий вызов создаёт новый payload и не накапливает прошлые
per-call условия. Text не выводит hard filters. Полная локальная проверка всех
query plans выполняется до HTTP; admission всех выбранных поколений — до первого
encode/search. При нескольких dense вариантах corpus SHA-256 всех admitted
поколений обязан совпадать. При `comparability.comparable=true` он также должен
совпадать с объявленным `cohort_sha256`; `evidence` фиксирует подтверждение владельца
OpenSearch. Search-only proxy не аттестует corpus digest внешнего индекса.

Bindings задают `type`, `opensearch_field`, `qdrant_path` и опциональный
`opensearch_source_path`. Последний — явный путь в исходном `_source` для карточки;
имя indexed field не обращается автоматически в путь данных, `.keyword` не
отбрасывается. Для dense карточка читает raw fields по `qdrant_path`. Отсутствующий
путь декларации, missing value и JSON null различаются. Эти пути не изменяют fields.
`study.fulltext_description_field` отдельно объявляет raw key полного описания
(default `description`): порядок scored fields не определяет поле карточки.

### Поисковые политики

F1 строит weighted best-fields literal query. F2 требует role/qualification core
и cross-field coverage, без literal bypass; guards сохраняют неоднозначный residual.
F3 применяет тот же eligibility и bounded multiplier; F4 строит disjoint
all/partial/none tiers с тем же core и boolean soft predicates. F5 объединяет
независимые F1/F2 выдачи существующим RRF. Одинаковый fallback получает один vote.
BM25 label требует явного similarity/analyzer evidence; без него артефакт сообщает
`native_lexical`. Реальная компиляция DSL и analyzers подтверждаются live G02/G08.

E1 кодирует исходный query. E2 сначала выбирает фиксированный topic pool, затем
exact scores всех его UUID через native `has_id` для topic-anchored preferences;
неполный набор ids или изменившиеся fields отклоняется. Основной bonus равен
`α × mean((cos+1)/2)`, контроль `min` — `α × min((cos+1)/2)`, без preferences bonus=0.
E3 независимо ищет original/topic и объединяет их RRF. E4 проверяет две distinct
ready title/body representations одного corpus, кодирует query один раз и делает
два retrieval. `SingleFieldText` сохраняет versioned recipe и полные исходные поля.
Derived query безопасно отображает normalized spans на original text; при
неоднозначном удалении применяется задекларированный abstention с исходным query.
Config/transport/response errors не становятся abstention.

E5 использует отдельный `ChunkVacancyText`, `ChunkQdrantSource` и
`ChunkIndexExperiment`. Payload/source schema=2, fragment schema=2 и
`fragment_layout=title-stop-bytes-v2` несовместимы с vacancy source v1. `title_stop`
и description start/stop — offsets UTF-8 normalized text; полный passage и prefixed
model input восстанавливаются локально, digest проверяется при payload admission,
hit conversion и full read-back. Deterministic UUIDv5 включает corpus identity,
recipe id, domain id, ordinal и digest model input. Fragment хранится отдельно от
неизменённых исходных fields. Token audit проверяет всё покрытие, overlap/progress,
64-title/384-body/64-overlap/max64 chunks; bounded encoding использует
`truncate=false`. Build проверяет N документов и все M points, indexes, payloads,
vectors и smoke до building→ready publication. Recipe change требует fresh name.

E5 query итеративно исключает уже найденные domain ids native filter и добирает
unique candidate depth; score вакансии — maximum passage score. Отказ поздней
итерации, stalled progress или повреждённый последний point отменяет весь вызов.
ANN режим сохраняет approximate provenance; exact режим явно отмечает tie boundary.
Количество passages не даёт sum bonus; opportunity bias остаётся исследовательским
вопросом, который локальные tests не решают.

### Снимок сравнения и рабочая сессия

`StudySERP` хранит отдельную evidence, `SearchStudyArtifact` — независимый deep
snapshot schema=1 `artifact_type=search-study`. Полные fields, final ranks,
score types, branch provenance, native timing, model inputs и фактические HTTP
counts остаются в артефакте; JSON/CSV прежних экспериментов не изменены. CLI session
имеет один run_id, а `comparison_run_id` сохраняет identity отдельных вводов.
`comparison_elapsed_ms` суммирует поиски, `session_elapsed_ms` включает ожидание ввода.

[search-study.ipynb](../src/experiments/notebooks/search-study.ipynb) использует
`StudyNotebookSession`: перед каждым новым compare сбрасывает `current`, принимает
query/variants/filter values/reference и сохраняет только полный успешный snapshot.
Rank lists, union matrix, полная карточка и diagnostics читают snapshot без
HTTP/inference. HTML экранируется; E5 winner passage виден отдельно. При
несопоставимых источниках fulltext/dense матрицы разделены; source differences
не скрываются. Численные score разных policies не сравниваются как одна шкала.

Явное `save` использует существующий atomic no-overwrite JSONExporter и путь
`outputs/search-study/<run_id>/search-study.json`. Advanced audit/build/batch/save
cells выключены по умолчанию. Compose/instantiate ничего не ищет и не строит;
изменение query/filters/selected registered subset не требует rebuild, изменение
параметров — новую composition, изменение document recipe/profile/corpus — fresh
поколения. Процесс/storage Qdrant и модельный runtime остаются user-owned.
