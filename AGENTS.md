# Работа над recsys-experiments

Проект реализует поисковые эксперименты на исходном каркасе `src/`. Исторические ветки помогают понять
намерения, но не задают обязательную архитектуру или toolchain новой версии.

## Перед изменениями

- При первом знакомстве прочитай [архитектуру](docs/architecture.md) целиком:
  она объясняет модель исполнения, назначение абстракций и сквозной сценарий.
  Она объясняет причины решений, которые нельзя вывести только из сигнатур.
- При изменении доменных типов и терминологии прочитай [CONTEXT.md](CONTEXT.md).
- При работе с данными, registry, transformers, интеграциями и экспериментами
  сверяйся с [архитектурными контрактами](docs/architecture.md): там описаны
  композиция через имена, общий payload, ветвления и ограничения на фильтры.
- Перед реализацией и выбором проверок прочитай
  [границы работы и текущий статус](docs/development.md). Там же перечислены
  свидетельства проверок и границы поставки.
- При изменении ranking, Query Understanding или русского контента рабочих профессий
  читай [spec 006](docs/specs/006-query-and-painless-candidates.md) и
  [приложение 006A](docs/specs/006-blue-collar-content.md). При изменении notebook
  или batch учитывай также [spec 005](docs/specs/005-search-research.md).
- [ZERO-SPEC](docs/ZERO-SPEC.md) сохраняет исходный замысел; последующие
  согласованные уточнения находятся в документах выше.

## Инженерные правила

- Преимущественно сохраняй заданную структуру абстракций. Сигнатуры — черновик:
  уточняй их под согласованные контракты. Существенную замену структуры согласуй.
- Эксперименты пишутся свободно на Python и используют типизированные компоненты.
  Владельцы поведения и доменные понятия должны быть явными.
- Весь код, включая конкретные реализации, размещай в `src/`.
- Всю конфигурацию задавай через Hydra; используй композицию и интерполяции
  для связывания компонентов. Предпочитай вложенную структуру каталогов
  длинным именам, например `configs/experiments/vacancy-ranking/task-1/001-baseline`.
- Пиши кратко и выразительно, с минимумом вспомогательных слоёв и runtime-проверок.
  Проверки внешних границ и обеспечение принятых инвариантов остаются необходимыми;
  не повторяй их без причины в каждом шаге pipeline.
- Меняй реализацию и её канонический контракт вместе. Термины принадлежат
  `CONTEXT.md`, технические контракты — `docs/architecture.md`, текущая готовность
  и границы поставки — `docs/development.md`.
- Перед кодом для нескольких компонентов сформулируй spec с наблюдаемым
  результатом, границами, failure semantics и acceptance evidence. Этот набор
  документов дополняется принятыми спеками; spec 001 реализована по явному запросу
  пользователя с автономным выбором тактических решений.

## Карта кода

| Каталог | Область |
| --- | --- |
| `src/domain/` | Документы, коллекции, запросы и фильтры |
| `src/core/` | Registry и transformers, выражающие pipeline |
| `src/integrations/` | Внешние системы и преобразование их представлений |
| `src/components/` | Компоненты оценки и отчётности в текущем каркасе |
| `src/experiments/` | Конкретные сценарии и orchestration |
| `src/run.py` | Точка входа Hydra и безопасное завершение CLI |

## Команды

Python 3.12+, Poetry 2.2+; зависимости и gates определены в `pyproject.toml` и `poetry.lock`.

```sh
poetry install
poetry run ruff check .
poetry run ruff format --check .
poetry run ty check
poetry run pytest
```

Для запуска и настройки подключения читай [README.md](README.md).
Тесты используют локальный HTTP-сервер; реальный прокси на текущем устройстве
недоступен. Не объявляй live smoke выполненным по результатам локальных тестов.
Для документационных изменений проверяй ссылки и `git diff --check`.
